## Done
- [x] The poster saved with every recorded clip is a base64 JPEG (~55 KB at the 1080-px long edge, 12.6 KB for a small clip) kept on the item for the rest of the session — and past its eviction — even though it is only a placeholder shown until the clip's first frame decodes. It was written into the viewer's `poster` attribute on every open and then left there, so every clip in the session carried a data URI nothing displayed. The poster is now released the moment the frame it was covering is on screen (`loadeddata`, or immediately when the clip is already decoded): `it.p` is cleared and the attribute removed, so the string only exists while it is the picture actually being shown. Nothing visible changes — the poster is replaced on screen by the frame at the same moment it is dropped. `tests/regress.js` checks it (26 checks, all passing; the new check reports 'poster kept' against the previous `index.html`). *(done 2026-11-04)*
- [x] Detail boost read the whole frame back and then copied all of it into a second full-size buffer so that every output pixel could read untouched source bytes: two 48 MB arrays at 12 MP, ~113 ms to allocate and copy, ~46 MB of live heap, allocated on the shutter's critical path — exactly the transient spike that gets a WebView killed on a low-end phone. The copy is gone: each row's original bytes are carried forward in two row-sized scratch arrays and the result is written straight back into the ImageData, so the boost holds one frame buffer instead of two. Every output pixel still reads only original bytes (the row above from the carry, the row below before it is written), so the output is byte-identical — checked across 27 size/strength combinations (3×3, 4×2, 2×9, odd sizes up to 4000×3000) and now asserted against a reference convolution in `tests/regress.js`. The row bands still yield between them, so the shutter animation keeps painting. *(done 2026-11-03)*
- [x] `Element.getAnimations()` only shipped in Chrome 84, four years after `el.animate()` (Chrome 36), so a WebView older than that has `animate()` but not `getAnimations()` — and all five call sites reached for it unguarded, every one of them on a hot path. The first line of `snap()` cancels the focus/flash ring, so the shutter threw before it read a frame and **no photo could be taken at all**; `toast()` threw before it wrote anything, so every capture, timer, zoom, flash and recording message was silent; `moveInd()` threw on every mode switch and resize, leaving the indicator behind; a focus tap and the countdown's cleanup threw too. Cancelling now goes through one guarded `killAnims(el)` helper: identical where the API exists, a no-op where it does not. Verified by a page that deletes `Element.prototype.getAnimations` before load — it boots, shows a toast and captures a photo (the previous `index.html` throws `t.getAnimations is not a function` and never captures). *(done 2026-11-03)*
- [x] Closing the viewer dropped the clip's `<video>` from the DOM with its blob source still attached: `done()` in `hideSheet()` cleared `#vm`'s markup and nothing released the media, so the last clip of every session stayed alive — decoder buffers, blob and all — until garbage collection. That is the same leak `renderView()` was fixed for on prev/next, on the far more common way out of the viewer. `stopViewMedia()` now runs before the markup is cleared, and only once the sheet is already hidden, so nothing on screen changes. *(done 2026-11-03)*
- [x] `countdown()` waited out its whole 1 s tick after a cancel, because the tick was a plain `sleep` with no way to interrupt it: the shutter, flip, zoom and mode buttons stayed locked behind `busy` for the rest of that second (809 ms measured) and answered "Wait for the timer to finish" for a timer that was already gone. The tick is now a cancellable wait that `cancelCd()` clears and resolves at once, so the countdown stops on the same frame, the `#cd` overlay is cleared, and a capture can never follow a cancel. *(done 2026-11-03)*
- [x] Native save handed the Android bridge 3 MB slices, and a `@JavascriptInterface` call does not return until the Java side has base64-decoded and written them, so saving a long take blocked the JS thread for the whole round trip in long bursts (3 MB becomes a 4 MB string). Slices are now 512 KB with a yield between them: an 8 MB clip crosses the bridge in 16 calls of at most 683 KB base64 instead of 3 calls of 4 MB, the longest main-thread stall measured end to end in `tests/regress.js` falls from 394 ms to ~120–200 ms, and in an isolated loop where only the bridge blocks it falls from 59.4 ms to 16.3 ms with the same total time (626 ms vs 612 ms). The reassembled bytes are identical to the clip, which the suite now checks. *(done 2026-11-03)*
- [x] Every slider `input` event wrote the whole config straight to `localStorage`. A single drag across the sheet emits ~60 events, so one drag ran 60 synchronous `JSON.stringify` + `setItem` calls — measured 60 calls / 22.3 ms inside `setItem` for 60 events, and each call is a storage commit in the WebView — interleaved with the frames that have to repaint the glass panel and the value readout. Writes are now coalesced: one commit 250 ms after the last change, plus an immediate flush on `change` (end of drag), `pagehide` and `visibilitychange` → hidden, so nothing is lost. Same 60 events now do 0 writes during the drag and exactly 1 on release; the stored config is byte-identical and settings still restore after a reload. *(done 2026-11-03)*
- [x] `spr()` rebuilt the 45-point spring curve (45 exp/cos/sin) and a fresh array of 45 keyframe objects with two template strings each on every call — ~0.38 ms of main-thread work and ~90 string allocations per bounce, on the tap that was supposed to start the animation, for endpoint pairs the app replays constantly (every control tap, every toast, every capture). The curve is now sampled once per bounce value and each keyframe set is built once and shared with `el.animate()` (which copies it); the cache is dropped when the bounce slider changes. Keyframes are byte-identical, verified against the old generator across 272 parameter/bounce combinations. *(done 2026-11-02)*

# Changelog

One entry per scheduled improvement run. Format: `date · run n/10 — what changed, and why`.

- **2026-11-01 · baseline** — v1.2 shipped: 4D tilt parallax, depth effect, consolidated Settings sheet, saved preferences. Repo restructured so the APK rebuilds from the repository layout (`app/src`, `app/res`, `app/keystore.jks`, `app/setup-toolchain.sh`), and `tests/regress.js` added as the standard verification pass.
- 2026-11-01 · run 1/10 — `items` is capped at 30 and dropped captures have their `blob:` object URL revoked; photos, recorded videos and native picks were never released, so a long session grew the JS heap without bound until the WebView was killed.
- 2026-11-01 · run 2/10 — `sharpScore()` now scores every burst candidate on one reused scratch canvas and one reused `Float32Array` instead of allocating a new 320-px canvas (~3 MB of RGBA) and grey buffer per frame, cutting ~15 MB of garbage per burst shot so the shutter animation and toast stay smooth on slow phones.
- 2026-11-01 · run 3/10 — `sharpen()` (Detail boost) processed the whole full-resolution frame in one synchronous loop, freezing the main thread for a few hundred ms at 12 MP right while the shutter animation and toast were running. It now works in ~1.5 M-px row bands and yields between them; output is byte-identical (verified across 4000×3000, odd, and degenerate frame sizes) and animation frames keep painting during the pass.
- 2026-11-01 · run 4/10 — `start()` now acquires the new stream before stopping the old one, so a failed camera flip or quality switch no longer leaves a black dead preview; a `NotReadableError`/`AbortError` from a still-held sensor releases the old tracks and retries once, and every exit path still stops the old tracks so no camera is left open.
- 2026-11-01 · run 5/10 — the video pipe's canvas loop redrew on every rAF tick (up to 60 fps) although `captureStream(30)` only samples it 30 times a second, so crop and the depth pass ran twice as often as they could ever be seen. The loop now skips frames that arrive before the next 1/30 s slot is due, halving the per-frame draw and depth work during recording without changing the captured video.
- 2026-11-01 · run 6/10 — the poster saved with every recorded clip was encoded from the full recording canvas (up to 3840×2160) inside `onstop`, so tapping stop ran a synchronous readback and JPEG encode of ~8 Mpx on the main thread (575 ms measured at 4K) and held a 236 KB base64 string per clip; it is now downscaled to a 1080-px long edge in one reused scratch canvas first (221 ms, 55 KB) — the poster is only a placeholder until the first video frame decodes and is drawn at thumb and phone size, so it looks the same.
- 2026-11-02 · run 7/10 — `#stage` was re-measured with `getBoundingClientRect()` on every `pointermove` (4D parallax) and on every drawn recording frame (`cropRect()` → `viewAspect()`), each read landing straight after the parallax loop wrote `style.translate` and therefore flushing a full synchronous layout — ~120 forced layouts a second while a finger drags a settings slider, ~30 a second while recording. The box is now measured once and cached (`stageBox()`), invalidated on `resize`; framing maths, the captured crop and the parallax mapping are unchanged, so the UI is pixel-identical.
- 2026-11-02 · run 8/10 — the viewer swapped `#vm`'s markup on every prev/next tap without stopping the clip that was playing, so each detached `<video>` kept its blob source and decoded frames alive until garbage collection and relied on Blink's implicit pause-on-removal to stop the audio. `renderView()` now pauses the outgoing video and releases its source first, so the decoder is freed immediately and playback can never continue in a browser that does not pause on detach.
- 2026-11-02 · run 9/10 — stopping a recording relied entirely on the recorder's `onstop` event. `MediaRecorder.stop()` only marks the recorder inactive and posts the stop task; when a WebView's media pipeline swallows it, `rec` stayed non-null for the rest of the session, so the shutter thought a take was still running, `#app` kept the `rec` state, the capture pipe kept drawing its canvas every frame and the microphone stayed open. Finalising the take is now one idempotent `finishRec()` that `onstop`, a throwing `stop()` and a 2 s watchdog armed by `stopRec()` all route through, so the clip is saved and everything released even when the event never arrives — verified by a harness that nulls `onstop` and confirms the take still lands and the recording state clears.
- 2026-11-02 · run 10/10 — every bounce re-sampled the 45-point spring curve (45 exp/cos/sin) and rebuilt 45 keyframe objects with two template strings each: ~0.38 ms of main-thread work and ~90 string allocations per call, on the tap that should start the animation, for endpoint pairs the app replays constantly (every control tap, every toast, every capture, every sheet). The curve is now sampled once per bounce value and each keyframe set is built once and reused — `el.animate()` copies the array, so sharing it is safe — with the cache dropped when the bounce slider changes. Keyframes are byte-identical to the old generator (checked across 272 parameter/bounce combinations), so motion and layout are unchanged; measured 2.32 ms → 1.98 ms per control bounce and 2.49 ms → 1.70 ms per toast, plus ~90 fewer string allocations each.
- 2026-11-02 · run 1/10 — every bounce handed `el.animate()` 45 evenly spaced spring keyframes and the browser resolved all of them (transform parse + interpolation setup, ~45 µs each), so a control tap spent ~3.0 ms and a toast ~3.9 ms on keyframes that a few straight segments draw identically. Interior samples whose removal keeps every dropped point within 0.35 px / 0.01 opacity of the chord the browser would draw are now pruned, with explicit `i/n` offsets so surviving keyframes keep their exact times: 45 → 19 keyframes for a control tap, 27 for a toast, 14 for a capture. Measured 3.00 → 1.68 ms per control bounce, 3.95 → 2.62 ms per toast, 5.01 → 1.71 ms per capture, and the rendered curve differs by at most 0.02 px of translateY and 0.0004 of scale (0.33 px on an 800 px box) with opacity identical — no visible change to any motion.
- 2026-11-02 · run 2/10 — a finished take's MediaRecorder chunks were only dropped when the *next* take started, so the raw recording data stayed pinned in the `chunks` array for the rest of the session — ~210 MB after a 60 s clip at the Max-quality 28 Mbps bitrate — even once the clip had been evicted from `items` and its object URL revoked, which defeated the 30-item memory cap. `cleanupRec()` now empties the array after `finishRec()` has built the clip's Blob (which keeps its own reference, so the video still saves and plays); verified the part-Blobs go from 85 KB retained to 0 after stop while the clip still lands and plays.
- 2026-11-03 · run 1/10 — every slider `input` event wrote the whole config to `localStorage`, so dragging one slider across the sheet ran ~60 synchronous `JSON.stringify` + `setItem` calls (measured 60 calls and 22.3 ms inside `setItem` for a 60-event drag, each one a storage commit in the WebView) in between the frames that repaint the glass panel and the value readout. The write is now coalesced — one commit 250 ms after the last change, flushed immediately on `change` (drag release), `pagehide` and a hidden `visibilitychange` — so the same drag does zero writes while the finger moves and exactly one when it lifts; the stored config is byte-identical and preferences still restore across a reload. The on-screen value still updates on every event, so nothing visible changes.
- 2026-11-03 · run 2/10 — saving a clip to the Gallery handed the Android bridge 3 MB slices, and a `@JavascriptInterface` call does not return until the Java side has base64-decoded and written them, so saving a long take froze the UI in long bursts (3 MB becomes a 4 MB string, and every round trip blocks the JS thread for its whole duration). Slices are now 512 KB with a yield between them: an 8 MB clip crosses the bridge in 16 calls of at most 683 KB base64 instead of 3 calls of 4 MB, and in an isolated loop where only the bridge blocks the longest main-thread stall falls from 59.4 ms to 16.3 ms with the same total time (626 ms → 612 ms); measured end to end through a stubbed bridge the longest stall falls from 394 ms to ~120–200 ms and the reassembled bytes are identical to the clip. `tests/regress.js` now drives the save through that stub and checks both the bytes and the slice size (18 checks, all passing; the new slice check fails against the previous `index.html`).
- 2026-11-03 · run 3/10 — the timer's 1 s tick was a plain `sleep` with no way to interrupt it, so cancelling a countdown only took effect when that tick ran out: the shutter, flip, zoom and mode buttons stayed locked behind `busy` for the rest of the second (measured 809 ms) and answered "Wait for the timer to finish" for a timer that was already cancelled. The tick is now a cancellable wait that `cancelCd()` clears and resolves immediately, so `busy` clears on the next frame, the `#cd` overlay is cleared at once, and a capture can never follow a cancel. The countdown itself, its sound, its animation and an uncancelled capture are unchanged (verified: a 10 s timer still fires, a cancelled one never captures). `tests/regress.js` now covers all three (21 checks, all passing; the new checks fail against the previous `index.html`).
- 2026-11-03 · run 4/10 — closing the viewer cleared `#vm`'s markup while the clip's `<video>` still held its `blob:` source, so the element was detached with its decoder buffers and blob alive until garbage collection: the last clip of every session leaked, and it is the most common way out of the viewer (the same leak `renderView()` was fixed for on prev/next). `stopViewMedia()` now pauses the clip and drops its source as the sheet's markup is cleared, once the sheet is already hidden, so nothing visible changes. `tests/regress.js` checks it (22 checks, all passing; the new check reports 'src kept' against the previous `index.html`), and the timer check no longer taps the shutter into a camera re-acquire after the flip test, which made it fail intermittently on the baseline.
- 2026-11-03 · run 5/10 — `Element.getAnimations()` arrived in Chrome 84, long after `el.animate()` (Chrome 36), and all five call sites used it unguarded — every one of them on a hot path. The first line of `snap()` cancels the focus/flash ring, so on an older WebView the shutter threw before it read a frame and no photo could be taken at all; `toast()` threw before it wrote anything, so every capture, timer, zoom, flash and recording message was silent; `moveInd()` threw on every mode switch and resize, leaving the mode indicator behind. Cancelling now goes through one guarded `killAnims()` helper, identical where the API exists and a no-op where it does not, so nothing visible changes on a current WebView. `tests/regress.js` now loads a page with `Element.prototype.getAnimations` deleted and checks that it boots, toasts and captures (24 checks, all passing; the new check reports `t.getAnimations is not a function` and no capture against the previous `index.html`).
- 2026-11-03 · run 6/10 — Detail boost read the whole frame back with `getImageData` and then copied all of it into a second full-size buffer so every output pixel could read untouched source bytes: two 48 MB arrays at 12 MP, ~113 ms to allocate and copy and ~46 MB of live heap, allocated right on the shutter's critical path — the transient spike that gets a WebView killed on a low-end phone. The copy is gone: each row's original bytes are carried forward in two row-sized scratch arrays and the result is written straight back into the ImageData, so the boost holds one frame buffer instead of two and skips the 48 MB copy. Every output pixel still reads only original bytes, so the boosted photo is byte-identical (verified across 27 size/strength combinations, 3×3 and 4×2 up to 4000×3000) and the row bands still yield between them, so nothing visible changes. `tests/regress.js` now checks the boosted bytes against a reference convolution (25 checks, all passing).
- 2026-11-04 · run 1/10 — every recorded clip kept its poster — a base64 JPEG standing in for the clip's first frame (~55 KB at the 1080-px long edge, 12.6 KB for a short one) — for the rest of the session, and past eviction, even though nothing shows it once that frame has decoded; it was rewritten into the viewer's `poster` attribute on every open and never released. The data URI is now dropped as soon as the frame it was covering is on screen (`loadeddata`, or at once when the clip is already decoded), so the string only exists while it is the picture being displayed — no visible change, since the poster and the first frame swap at the same moment. `tests/regress.js` checks it (26 checks, all passing; the new check reports 'poster kept' against the previous `index.html`).
- 2026-11-04 · run 2/10 — the tap sound created one `AudioContext` on the first press and left it running for the rest of the session: a running context holds the audio output stream open, so the device's audio hardware never idles down between the ~0.2 s blips the app plays — the audio DSP and its clock held awake for the whole time the camera is open, for silence (measured: `AC.state` still `running` 6 s after the last sound, and still `running` with the page hidden). It is now suspended 1.2 s after the last sound — longer than the countdown's 1 s tick, so a running timer keeps it awake across its own beeps instead of sleeping and waking once a second — and immediately when the page is hidden; `plop()` resumes it inside the tap that caused it, so it is still a user gesture, and the unhandled rejection a refused `resume()` used to raise is caught. The sound itself is unchanged: two oscillators and the noise burst are still scheduled on every tap, including the first one after a sleep. `tests/regress.js` drives the whole cycle (30 checks, all passing; the sleep and hidden checks report `running` against the previous `index.html`).

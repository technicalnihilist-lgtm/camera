# Changelog

One entry per scheduled improvement run. Format: `date · run n/10 — what changed, and why`.

- 2026-11-07 · run 4/10 — the take's microphone request was the one await in the recording path with no natural end, and the only one that holds the whole app. `busy` is set before the countdown and the mic is asked for inside the same try/finally, so the flag came off only once `getUserMedia({audio:true})` settled — and a permission prompt that is never answered (dismissed by clicking beside it in a desktop browser, or a request a WebView drops when its activity is torn down) leaves that promise pending for ever. `busy` then stayed true and the shutter, flip, zoom, mode, timer and record buttons all answered "Wait for the timer to finish" until the app was restarted; reproduced in headless Chromium with a mic stub that never settles — the previous `index.html` never starts the take and `busy` is still true after a second shutter tap, this one records. The wait is bounded now, and the bound follows what the browser reports for the permission: a granted microphone that has not opened in 5 s is a wedged audio HAL, a prompt on screen is a person being asked and gets 20 s, and a denied microphone is answered from the permission state instead of by a request that can only be rejected. A stream that arrives after the bound has fired is stopped on arrival, so giving up can never leave the microphone open, and the take falls back to the state the app already has for a missing mic — it records without sound. Nothing visible changes. `tests/regress.js` adds five checks (59, all passing; five of them fail against the previous `index.html`, which never starts the take and leaves `busy` true). Also: this run's daily APK rebuild bumps versionCode to 9 and versionName to 1.8.
- 2026-11-07 · run 3/10 — the 4D parallax smoothing stepped a flat 0.14 every frame, so how long the glass layers took to settle was decided by the display's refresh rate rather than by time: 20 frames is 333 ms at 60 Hz but 167 ms at 120 Hz, so on a 120 Hz phone (most current Androids) the parallax snapped to the tilt in half the time it was tuned for, while a WebView that fell to 30 fps dragged the same move out to 667 ms — the motion model was frame-rate dependent even though the README describes it as a frame-rate-independent lerp. `parLoop()` now scales the step by the frame's own interval, normalised to a 60 Hz frame, so a normal 60 Hz cadence steps by exactly the same 0.14 and nothing about the motion changes there; the interval is clamped at 50 ms so the first frame after a long pause eases in rather than jumping, and it is dropped when the loop parks so the next kick starts fresh. Measured with a virtual animation clock: 60 Hz 20 frames / 333 ms and 120 Hz 40 frames / 333 ms, against 20 / 333 ms and 20 / 167 ms before, and the 60 Hz trajectory is unchanged (0.595 of the way at 100 ms). `tests/regress.js` drives the loop from a virtual `requestAnimationFrame` clock at 60 and 120 Hz (53 checks, all passing; the new check fails against the previous `index.html`). Nothing visible changes.

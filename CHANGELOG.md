# Changelog

One entry per scheduled improvement run. Format: `date · run n/10 — what changed, and why`.

- **2026-11-01 · baseline** — v1.2 shipped: 4D tilt parallax, depth effect, consolidated Settings sheet, saved preferences. Repo restructured so the APK rebuilds from the repository layout (`app/src`, `app/res`, `app/keystore.jks`, `app/setup-toolchain.sh`), and `tests/regress.js` added as the standard verification pass.
- 2026-11-01 · run 1/10 — `items` is capped at 30 and dropped captures have their `blob:` object URL revoked; photos, recorded videos and native picks were never released, so a long session grew the JS heap without bound until the WebView was killed.
- 2026-11-01 · run 2/10 — `sharpScore()` now scores every burst candidate on one reused scratch canvas and one reused `Float32Array` instead of allocating a new 320-px canvas (~3 MB of RGBA) and grey buffer per frame, cutting ~15 MB of garbage per burst shot so the shutter animation and toast stay smooth on slow phones.
- 2026-11-01 · run 3/10 — `sharpen()` (Detail boost) processed the whole full-resolution frame in one synchronous loop, freezing the main thread for a few hundred ms at 12 MP right while the shutter animation and toast were running. It now works in ~1.5 M-px row bands and yields between them; output is byte-identical (verified across 4000×3000, odd, and degenerate frame sizes) and animation frames keep painting during the pass.
- 2026-11-01 · run 4/10 — `start()` now acquires the new stream before stopping the old one, so a failed camera flip or quality switch no longer leaves a black dead preview; a `NotReadableError`/`AbortError` from a still-held sensor releases the old tracks and retries once, and every exit path still stops the old tracks so no camera is left open.
- 2026-11-01 · run 5/10 — the video pipe's canvas loop redrew on every rAF tick (up to 60 fps) although `captureStream(30)` only samples it 30 times a second, so crop and the depth pass ran twice as often as they could ever be seen. The loop now skips frames that arrive before the next 1/30 s slot is due, halving the per-frame draw and depth work during recording without changing the captured video.
- 2026-11-01 · run 6/10 — the poster saved with every recorded clip was encoded from the full recording canvas (up to 3840×2160) inside `onstop`, so tapping stop ran a synchronous readback and JPEG encode of ~8 Mpx on the main thread (575 ms measured at 4K) and held a 236 KB base64 string per clip; it is now downscaled to a 1080-px long edge in one reused scratch canvas first (221 ms, 55 KB) — the poster is only a placeholder until the first video frame decodes and is drawn at thumb and phone size, so it looks the same.
- 2026-11-02 · run 7/10 — `#stage` was re-measured with `getBoundingClientRect()` on every `pointermove` (4D parallax) and on every drawn recording frame (`cropRect()` → `viewAspect()`), each read landing straight after the parallax loop wrote `style.translate` and therefore flushing a full synchronous layout — ~120 forced layouts a second while a finger drags a settings slider, ~30 a second while recording. The box is now measured once and cached (`stageBox()`), invalidated on `resize`; framing maths, the captured crop and the parallax mapping are unchanged, so the UI is pixel-identical.
- 2026-11-02 · run 8/10 — the viewer swapped `#vm`'s markup on every prev/next tap without stopping the clip that was playing, so each detached `<video>` kept its blob source and decoded frames alive until garbage collection and relied on Blink's implicit pause-on-removal to stop the audio. `renderView()` now pauses the outgoing video and releases its source first, so the decoder is freed immediately and playback can never continue in a browser that does not pause on detach.
- 2026-11-02 · run 9/10 — stopping a recording relied entirely on the recorder's `onstop` event. `MediaRecorder.stop()` only marks the recorder inactive and posts the stop task; when a WebView's media pipeline swallows it, `rec` stayed non-null for the rest of the session, so the shutter thought a take was still running, `#app` kept the `rec` state, the capture pipe kept drawing its canvas every frame and the microphone stayed open. Finalising the take is now one idempotent `finishRec()` that `onstop`, a throwing `stop()` and a 2 s watchdog armed by `stopRec()` all route through, so the clip is saved and everything released even when the event never arrives — verified by a harness that nulls `onstop` and confirms the take still lands and the recording state clears.
- 2026-11-02 · run 10/10 — every bounce re-sampled the 45-point spring curve (45 exp/cos/sin) and rebuilt 45 keyframe objects with two template strings each: ~0.38 ms of main-thread work and ~90 string allocations per call, on the tap that should start the animation, for endpoint pairs the app replays constantly (every control tap, every toast, every capture, every sheet). The curve is now sampled once per bounce value and each keyframe set is built once and reused — `el.animate()` copies the array, so sharing it is safe — with the cache dropped when the bounce slider changes. Keyframes are byte-identical to the old generator (checked across 272 parameter/bounce combinations), so motion and layout are unchanged; measured 2.32 ms → 1.98 ms per control bounce and 2.49 ms → 1.70 ms per toast, plus ~90 fewer string allocations each.
- 2026-11-02 · run 1/10 — every bounce handed `el.animate()` 45 evenly spaced spring keyframes and the browser resolved all of them (transform parse + interpolation setup, ~45 µs each), so a control tap spent ~3.0 ms and a toast ~3.9 ms on keyframes that a few straight segments draw identically. Interior samples whose removal keeps every dropped point within 0.35 px / 0.01 opacity of the chord the browser would draw are now pruned, with explicit `i/n` offsets so surviving keyframes keep their exact times: 45 → 19 keyframes for a control tap, 27 for a toast, 14 for a capture. Measured 3.00 → 1.68 ms per control bounce, 3.95 → 2.62 ms per toast, 5.01 → 1.71 ms per capture, and the rendered curve differs by at most 0.02 px of translateY and 0.0004 of scale (0.33 px on an 800 px box) with opacity identical — no visible change to any motion.
